# 設計書：ステークホルダー会議室（Policymaking Board）

> 型の契約：`src/lib/types.ts`（これが唯一の正）。会議の種類の調査：`docs/01-research-meeting-types.md`。

## 0. コンセプト
社会のさまざまな立場（国 × 役割）を持つAIが1つの議題を話し合う会議室。ユーザーは参加者・議題・会議の種類・進行役を決めて会議を開き、2.5Dの会議室で議論が進む様子を見る。会議後は議事録、決定事項・提言、落とし所、各参加者の納得度を確認できる。

## 1. 技術スタック
- Next.js 15（App Router）+ TypeScript + Tailwind CSS 4
- 状態管理：zustand（`src/store/`）。会議の履歴は localStorage に保存（キー `pmb:meetings:v1`）
- LLM：`@anthropic-ai/sdk`。サーバー側の Route Handler だけから呼ぶ。キーは環境変数 `ANTHROPIC_API_KEY`
- 構造化出力：`client.messages.parse` + `zodOutputFormat`（`@anthropic-ai/sdk/helpers/zod`）
- **モックモード**：`ANTHROPIC_API_KEY` が未設定、または `PMB_MOCK=1` のとき、エンジンは決定的なダミー応答を返す。UIの開発とテストを課金なしで回すため。モックでも全フェーズ → 閉会 → 結果画面まで完走できること
- 描画：SVG + CSS（2.5D）。外部画像アセットは使わない

## 3. 会議エンジン

### 3.1 ステートレスなターン駆動
サーバーは状態を持たない。クライアントが `MeetingState` を持ち、`POST /api/meeting/step` に送ると、サーバーが「次の1ターン」を計算して差分を返す。こうすると一時停止・再開・ページ再読み込み（localStorage から復元）が簡単になり、サーバーレスでも動く。

```
POST /api/meeting/step
  req:  { state: MeetingState }
  res:  { utterances: Utterance[];          // 進行役の発言（あれば）＋話者の発言
          minutes?: Minutes;               // 書記が更新したときだけ
          phaseIndex: number; phaseTurn: number; turn: number;
          status: MeetingStatus;           // 終了判定で "closing" になる
          initialStances?: ...;            // 初回ターンだけ
          usage: UsageTotals }             // 累計
POST /api/meeting/close
  req:  { state: MeetingState }
  res:  { outcome: MeetingOutcome; usage: UsageTotals }
```
クライアントは status が running の間 step を繰り返し、closing になったら close を呼んで結果画面へ移る。速度設定（待ち時間 0〜3秒）と一時停止をUIで操作できる。

### 3.2 1ターンの流れ（step）
1. **進行役の判断**（facilitator）：現在のフェーズ、フェーズ内のターン数と予算、最近の発言、議事要旨、未発言・発言が少ない人をもとに `FacilitatorDecision` を返す。
   - `roundRobin` のフェーズでは、次の話者を発言順のリストからコードで決め、LLMには進行役の短い発言と話者への指示だけを書かせる（費用削減）
   - フェーズ予算を超えたら `advancePhase` を強制する。全フェーズが終わったら `endMeeting`
2. **進行役の発言**：`facilitatorRemark` が空でなければ `kind:"facilitation"` の Utterance にする
3. **話者の発言**（speaker）：話者の人物設定、開示レベルのルール、議題、議事要旨、直近の発言（最大20件）、進行役の指示から `SpeakerOutput` を作る。新しい提案は Proposal として追加し、`proposalStances` を support に反映する
   - 進行役が自分を指名した場合（論点整理やとりまとめ案）は、同じ人物が進行役として話す
4. **書記**（scribe）：3ターンごと、またはフェーズの切り替わりで、`Minutes` を増分更新する（要旨、論点ごとの立場マップ、落とし所の候補、重要なやりとり、提案のステータス）
5. 初回ターンの前に**初期スタンス**を一括で生成する（参加者ごとの立場の1行要約とスタンス。1回の呼び出しで全員分）

### 3.3 閉会（close）
1. **納得度の自己申告**：参加者ごとに、その人物としてのモデルで `SatisfactionReport` を作る（並列実行）。自分の利害に照らして正直に（オフレコでなくても、ここはユーザーにだけ見える「アンケート」という扱い）
2. **最終とりまとめ**：上位モデルで `MeetingOutcome` を作る。決定事項の最終ステータスは合意ルールに従って判定する（例：コンセンサスでは1人でも consent=1 がいれば不成立 → 両論併記または継続審議）。落とし所、各ステークホルダーの言い分、重要なやりとり、未解決の論点、次のステップ、正式な議事録（Markdown）を含む
3. 合意ルールの機械的な判定（多数決の集計、コンセンサスのブロック判定）はコードで行い、結果をプロンプトに渡す。LLMに数えさせない

### 3.4 モデルの割り当て（`lib/engine/models.ts`）
| 担当 | economy | standard（既定） | premium |
|---|---|---|---|
| 話者 speaker | claude-haiku-5-5 | claude-sonnet-5-5 | claude-sonnet-5-5 |
| 進行役 facilitator | claude-haiku-5-5 | claude-sonnet-5-5 | claude-opus-5-5 |
| 書記 scribe | claude-haiku-5-5 | claude-haiku-5-5 | claude-sonnet-5-5 |
| 初期スタンス | claude-haiku-5-5 | claude-haiku-5-5 | claude-sonnet-5-5 |
| 納得度の自己申告 | claude-haiku-5-5 | claude-sonnet-5-5 | claude-sonnet-5-5 |
| 最終とりまとめ closing | claude-sonnet-5-5 | claude-opus-5-5 | claude-opus-5-5 |

- effort：speaker と scribe は `low`、facilitator は `low`（premium は `medium`）、closing は `high`。`output_config: { effort, format }`
- thinking は指定しない（各モデルの既定の adaptive）。Opus 5.5 と Sonnet 5.5 では `disabled` を送ると400になる
- 料金表（USD/100万トークン、入力/出力）：Opus 5.5 は 4/20、Sonnet 5.5 は 2/10、Haiku 5.5 は 0.1/0.5。キャッシュ読み込みは入力の約1/10で概算する
- **プロンプトキャッシュ**：system は「固定の会議ルール＋人物設定」だけにして、変動する内容（議事要旨・直近の発言）は messages 側に置く。リクエストの最上位に `cache_control: {type:"ephemeral"}` を付ける。system に日時やIDを入れない
- エラー：`Anthropic.RateLimitError` と 5xx は1回だけ待って再試行する（SDK既定の再試行に任せてもよい）。`stop_reason === "refusal"` や parse 失敗のときは、その話者の発言を「（発言を控えた）」にして会議を続ける。会議は止めない
- `messages.parse` の `parsed_output` が null の場合も同じフォールバックにする

## 4. 人物生成（`lib/participants.ts`）
- `createParticipant(roleId, countryCode, seed)`：seed（文字列ハッシュ）から決定的に、性別・年齢（役割の ageRange 内）・名前（国の名前プール）・肌の色（国の skinTones から）・髪型・髪色（年齢が高いと白髪の確率が上がる）・服の色・眼鏡を決める。personality は短い性格の候補リスト（30個程度）から選ぶ
- 同じ役割を同じ国から2人入れてもよい（名前で区別できる）
- 席の配置：`seatIndex` は追加順。進行役は議長席（上座、インデックス0の席）に移す

## 5. プロンプト設計（品質の要。`lib/engine/prompts.ts` はこの内容を忠実に実装する）

### 5.1 共通：開示レベルのルール（DISCLOSURE_RULES）
```
public:   この会議は公開され、議事録は発言者名つきで公表され、報道もされる。あなたの発言は、あなたが所属する組織・支持者・有権者・顧客・同僚・家族にも見られる。組織の公式見解や建前を中心に、言質を取られないよう慎重に話す。本当の事情（privateConcerns）は口にしない。ただし innerThought には本音を書く。
closed:   非公開の会議。議事要旨は発言者名なしで公表される。公式見解に加えて、背景の事情や現場の実感を率直に話してよい。ただし組織の機密や個人的な損得はぼかす。
chatham:  チャタムハウス・ルール。内容は外で使われるが、誰が言ったかは明かされない。個人としての本音、組織内の異論、不確かな見通しを話してよい。
offrecord: 完全なオフレコ（根回し・非公式協議）。記録は残らない。本当の利害（予算、票、ポスト、業界の内情、譲れる線・譲れない線、交渉が決裂した場合の代替案）を明かし、取引を持ちかけてよい。生々しく、しかし人物として自然に。
```

### 5.2 話者の system（固定部分。人物ごとにキャッシュされる）
```
あなたは会議に参加している一人の人間「{name}」（{age}歳、{country.name}、{role.title}）として発言する。AIであることには触れない。
## あなたの人物像
{role.description}
性格：{personality}
国・社会の状況：{country.context}
## あなたの利害
大事にしていること（インタレスト）：{interests}
不安・プレッシャー：{concerns}
人には言いにくい事情：{privateConcerns}
立場上の制約：{constraints}
## 話し方
{role.speechStyle} {country.speechNote}
専門知識のレベル：{expertise}/100（低ければ専門用語を使わず、生活の言葉で話す）
## 会議
種類：{meetingType.name}（{meetingType.description}）
開示レベル：{DISCLOSURE_RULES[disclosure]}
合意ルール：{decisionRuleText}
議題：{topic}
背景：{background}
参加者：{participants: 名前（国・役割）のリスト。進行役には印}
## 発言のルール
- 自分の立場の利益を真剣に代弁する。物分かりがよすぎる人にならない。安易に全員と合意しない。ただし、納得できる理由や見返りがあれば立場を動かしてよい。そのときは何が決め手かを明確にする
- 他の参加者の名前を出して応答・反論・質問してよい。直前の発言をただ繰り返さない
- 具体的に話す：自分の生活・仕事の具体例、数字、現場のエピソード
- 発言は1〜4文、多くても200字程度（中高生や現場の人はより短く、口語で）
- 「ポジション」の奥の「インタレスト」を意識する。対立していても両立できる方法があれば提案する
- 新しい具体的な案を出すときは newProposal に書く
- innerThought には、その発言をした本当の理由・計算・感情を書く（他の参加者には見えない）
```
進行役のときは、system の最後に次を追加する：「あなたは本来の立場を持ったまま、この会議の進行役（座長）も務める。中立的に進めようと努めるが、自分の立場がにじむことがある」。

### 5.3 話者の user メッセージ（毎ターン変わる部分）
```
## 現在のフェーズ：{phase.name}（目的：{phase.goal}）
## これまでの議事要旨
{minutes.summary}
## 議題に上がっている提案
{proposals: id / タイトル / 提案者 / 状態 / 支持状況}
## 直近の発言
[発言者名（役割）] 発言 ...（最大20件）
## 進行役からの指示
{directive.prompt}
あなたの番です。
```

### 5.4 進行役の判断（facilitator）
system：進行役の人物設定（5.2 と同じ人物）＋「あなたは座長としての判断をする」。user：フェーズ一覧と現在地、フェーズ内のターン数と予算、参加者ごとの発言回数とスタンス、議事要旨、直近の発言、提案一覧。
判断の指針：
- 発言の少ない人や、まだ立場が見えていない人を優先する。特に影響力の小さい立場（中学生、現場の人）を置き去りにしない
- 対立が出たら、当事者同士に直接応答させる。論点が煮詰まったら、インタレストに戻る質問をする（「なぜそれが大事なのですか」）
- とりまとめ・合意確認のフェーズでは、自分（進行役）がとりまとめ案を提示し、各人に賛否を確認する
- 公開会議では形式的で丁寧に、オフレコでは砕けた調子で、交渉では争点を絞る
- `facilitatorRemark` は短く（0〜2文）。毎ターン話す必要はない（つなぎが不要なときは空にする）

### 5.5 書記（scribe）
system：「あなたは事務局の書記。発言しない。中立的で正確な議事録を作る」。入力：前回の Minutes（JSON）、新しい発言、参加者の一覧。出力：更新した Minutes。
- `summary` は議事要旨のスタイル（「〜との意見があった」）で200〜500字に保ち、古い内容は圧縮する
- `issues`：論点ごとに、各参加者の position（表向きの主張）、interest（推測される本当の利害）、stance。合意の芽があれば landingZone を書く
- `keyExchanges`：転機になったやりとりだけ（対立の顕在化、取引、譲歩、言い換えによる突破、連携）。会議全体で3〜8個
- `proposals`：status と support を更新する。提案のIDは変えない

### 5.6 納得度の自己申告と最終とりまとめ
- 自己申告：その人物として、会議全体と最終案を振り返り、`SatisfactionReport` を出す。score と consent が整合するようにする（consent 1 なら score は30以下が目安）。自分の利害に照らして正直に。中高生には中高生の言葉で書かせる
- 最終とりまとめ（Opus）：全発言の要約、Minutes、自己申告、合意ルールの集計結果（コードで計算したもの）から `MeetingOutcome` を作る。landingZone は「誰が何を譲り、何を得たか」がわかる書き方にする。minutesMarkdown は日本の審議会の議事録の体裁にする（日時、出席者、議題、議事概要、決定事項、今後の予定）

## 6. 画面設計

### 6.1 ホーム（`/`）
タイトル、「新しい会議を開く」ボタン、過去の会議一覧（議題・種類・日付・状態。クリックで会議または結果へ）。

### 6.2 セットアップ（`/setup`）：1画面に3つのステップ
左（幅40%）：**参加者を選ぶ**
- 国のセレクター（国旗＋国名）とカテゴリのタブ（学生・若者 / 教育 / 家庭・地域 / 地方行政 / 国政 / 企業経営 / 働く人 / 技術者 / 医療・福祉 / 市民社会 / 農林水産 / 専門家）、検索ボックス
- 役割カード：小さなアバターのプレビュー、肩書き、説明の1行。クリックで追加すると、右の会議室に着席アニメーション
- おすすめの組み合わせ（プリセット）：例「教育改革（生徒・教師・親・教育委員会・文科大臣…）」「地方交通の維持」「AIと雇用」

右（幅60%）：**会議室のプレビュー**（§7 の Room をそのまま使う）
- 着席したアバターをクリックすると、ポップオーバーに人物情報（名前・年齢・国・役割・性格）、「進行役に任命」「名前を振り直す」「退席させる」
- 進行役には議長席の札と小槌のアイコン

下部：**議題と会議の種類**
- 議題（必須）と背景（任意）。議題の例をチップで表示（「高校の部活動の地域移行」「ライドシェアの全面解禁」「生成AIの学校での利用ルール」など）
- 会議の種類カード（10種類）：名前、説明、開示レベルのバッジ（公開 / 非公開 / チャタム / オフレコ）、合意ルール、典型的な成果物。選ぶと、部屋の内装がそのテーマに変わる
- 詳細設定（折りたたみ）：開示レベルの上書き、合意ルールの上書き、長さ（短い / 標準 / 長い）、モデルの品質（エコノミー / 標準 / プレミアム）と、1回の会議の概算コストの目安
- 「開会する」ボタン：参加者2人以上、進行役あり、議題ありで有効になる

### 6.3 会議中（`/meeting/[id]`）
- 上部バー：議題、会議の種類、開示レベルのバッジ、**フェーズの進捗**（ステップ表示。現在のフェーズを強調）、ターン数、累計コスト
- 中央：会議室（全幅で大きく）
  - 発言中の人：吹き出しで文字送り表示（20〜40文字/秒）、スポットライト、口パク（SVGの口の開閉）、少し前に乗り出す
  - 他の人はスタンスに応じた表情（眉と口）。うなずき、腕組み（concern/oppose）
  - **本音モード**（トグル）：各アバターの頭上に innerThought を薄い思考の雲として表示。オフレコ会議では既定でON
  - 部屋の正面のホワイトボードやスクリーンに、現在のフェーズ名と検討中の提案のタイトル
- 右パネル（タブ、幅380px、折りたたみ可）
  1. **発言録**：時系列。アバターのアイコン、名前、スタンスの色の帯、本音は折りたたみ
  2. **議事要旨**：書記の summary とフェーズごとの要点
  3. **論点マップ**：論点ごとに、参加者の立場を「支持 ← → 反対」の軸上にアバターで配置。position と interest は hover で表示。落とし所の候補をハイライト
  4. **提案・決定**：提案カード（タイトル、本文、提案者、状態のバッジ、参加者ごとの支持のドット）
  5. **重要なやりとり**：KeyExchange のカード（種類のアイコン：⚡対立 / ⇄取引 / 💡突破 / 🤝譲歩 / 🔗連携 / 🔄言い換え）。クリックすると発言録の該当箇所へ移動
- 下部の操作バー：▶開始 / ⏸一時停止 / ⏭1ターン進める、速度、**閉会する**（進行役に「まとめに入ってください」と指示 → 最後のフェーズへ移る）

### 6.4 結果（`/meeting/[id]/results`）：ダッシュボード
1. ヘッダー：成果物のタイトル（「答申（案）」など）、議題、日時、参加者のアバターの列
2. **エグゼクティブサマリー**
3. **落とし所**：大きなカードで、誰が何を譲り、何を得たか
4. **決定事項・提言・政策案**：ステータス別（合意 / 条件付き合意 / 両論併記 / 継続審議 / 否決）。条件と支持の内訳
5. **納得度**：参加者ごとの横棒グラフ（0〜100、色は consent の5段階）。行を展開すると、納得している点 ✅ / 納得していない点 ❌ / 残る懸念 ⚠️ / 希望 🌱 と本人のコメント（吹き出し）。スタンスの変化（開会時 → 閉会時）を矢印で
6. **各ステークホルダーの言い分**：主張と、その奥にある本当の利害のカード
7. **重要なやりとり**：タイムライン形式で、引用された発言つき
8. **未解決の論点と次のステップ**
9. **議事録**（Markdown を描画）＋「Markdownでダウンロード」「JSONでエクスポート」

## 7. ビジュアル設計（2.5D会議室）

### 7.1 方式
- 1つの `<svg viewBox="0 0 1600 900">` に部屋全体を描く。斜め上から見下ろす視点（床は台形のパース。不等角投影の厳密さは求めない）
- 奥から手前へ描く：壁 → 窓・装飾 → 床 → 奥の席のアバター → 机 → 手前の席のアバター（机に隠れる）。奥の席は机の向こうに上半身、手前の席は後ろ姿にしない（簡略化のため、手前の席も机の手前側から斜めにこちらを向く上半身として描く）
- 光：窓からの光の筋（グラデーション）、天井照明の柔らかい放射グラデーション、机の天板の反射のハイライト
- 部屋のテーマ（`RoomTheme`）ごとに内装を変える
  - `council_chamber`（審議会）：木の壁パネル、長いコの字の机、各席にマイクと名札、ペットボトルの水、正面にスクリーン、奥に国旗と省庁のエンブレム風の装飾（架空のもの）、深緑の絨毯
  - `roundtable_hall`（円卓会議）：明るいモダンな部屋、大きな楕円の机、ガラスの壁越しに都市の景色、観葉植物、壁にホワイトボードと付箋
  - `townhall`（タウンミーティング・公聴会・市民会議）：公民館風。木の床、長机を半円に配置、壁に「〇〇市」の横断幕、パイプ椅子、窓の外に山と田畑
  - `backroom`（根回し・交渉）：和室の料亭風。畳、座卓、障子越しの夜の光、掛け軸、床の間、行灯の暖色の照明。または夜のホテルのラウンジ風（交渉はラウンジ、根回しは和室）
  - `cabinet_room`（閣議・委員会）：重厚な楕円の机、革張りの椅子、シャンデリア、赤い絨毯、金の装飾
- 席の座標：テーマごとに、最大16席の座標リストと向きを持つ。席数に応じて使う席を選ぶ（等間隔に配置）。席0は議長席
- 窓の外の空：時刻（実際の現在時刻）で、朝・昼・夕・夜を切り替える

### 7.2 アバター（`components/room/Avatar.tsx`）
- `AvatarSpec` から決定的に描く。上半身、正面〜やや斜め。サイズは約120×150で、`scale` で縮小できる
- パーツ：顔の輪郭、肌の色（6色）、髪型8種類（短髪、七三、坊主、ボブ、ロング、ポニーテール、お団子、薄毛）と髪色、目、眉（表情で角度が変わる）、口（表情と口パク）、年齢の表現（40歳以上でほうれい線、60歳以上で白髪の割合）、眼鏡
- 服（Outfit）を役割ごとに描き分ける：学ラン/セーラー服（中学生）、ブレザー（高校生）、スーツ＋ネクタイ、大臣/総理は濃紺のスーツ＋議員バッジ、バス運転手は制帽＋制服、エンジニアは作業着＋ヘルメット、ソフトウェアエンジニアはパーカー＋ノートPC、医師は白衣＋聴診器、農家は作業着＋帽子、教師はカーディガン＋名札
- 表情（props `expression`：neutral / smile / concern / frown / thinking / surprised）、`speaking`（口パク）、`highlight`（スポットライト）
- 名札（三角柱の名札を机の上に）：「肩書き 名前」と国旗の絵文字

### 7.3 動き（CSSアニメーション）
- 着席：椅子の後ろから下りてくる（translateY + opacity、400ms）
- 発言中：上下に揺れる（2px）、口パク（150ms間隔）
- 待機中：まばたき（ランダムな間隔）、たまにうなずく
- 吹き出し：ふわっと出る。長い文章はスクロールせず、最大4行で省略し、発言録で全文を読める

## 8. 品質基準（レビューの観点）
- `npm run build` と `npm run lint` が通る。型エラーがない
- モックモードで、セットアップ → 会議 → 閉会 → 結果まで完走できる
- APIキーはクライアントに出ない。`/api` 以外から SDK を import しない
- エンジンは parse の失敗や拒否で会議を止めない
- 日本語のUI。スマホ幅（375px）でも崩れない（会議室は縮小表示、パネルは下に回る）
- 発言の多様性：同じ人が3回連続で話さない（進行役のとりまとめを除く）
